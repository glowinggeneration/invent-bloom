# SMAIT

SMAIT is a communications-intelligence and campaign-operations platform. It brings monitoring, narrative intelligence, message testing, campaign operations, measurement and reporting into one authenticated product.

## Product flow

The main operating loop is:

**Monitor → Understand → Decide → Test → Run → Measure**

Key surfaces include:

- **Overview** for brand health, intelligence briefs, narratives, risks, opportunities and recommended actions.
- **Mentions** for X, news and connected social monitoring with sentiment, importance, source authority and investigation filters.
- **Executive Brief** and **Crisis Command** for leadership and fast-moving issue response.
- **Response Studio** and **Compare Messages** for persona-based message testing.
- **Campaign Preflight**, **Campaign Manager** and **Campaign Proof** for controlled execution and defensible campaign records.
- **Performance**, **Reports** and **Custom Report Builder** for measurement and exports.
- **Monitoring Watchlist** and **Decision Log** for intelligence priorities and institutional memory.
- **X Account Health** and **System Health** for operational readiness.
- **Help Centre**, **Governance & Data** and **Changelog** for user guidance and governance.

## X campaign safeguards

Campaign execution is compliance-aware. The platform separates monitoring from execution and blocks legacy coordinated patterns such as fleet-wide Likes, automated proactive following, peer self-boosting, Watchlist-triggered engagement, several linked accounts targeting the same external post, and materially duplicated multi-account copy.

Account-level activity budgets, queue cooldowns, failure backoff, account challenge holds and a workspace emergency pause protect campaign operations. These are internal operational guardrails, not reverse-engineered platform-enforcement thresholds.

## Development

The project uses TanStack Start, React, TypeScript, Vite and Supabase. Dependencies are managed with [Bun](https://bun.sh) (`bun.lock` is the lockfile of record).

```sh
bun install
bun run validate
```

`validate` runs the full test, build, typecheck and lint sequence. Individual steps (`bun run test`, `bun run build`, `bun run typecheck`, `bun run lint`) can be run on their own too.

For local development:

```sh
bun run dev
```

`src/routeTree.gen.ts` is generated by TanStack Router. Do not hand-edit it. Running the Vite/TanStack build regenerates the route tree from files under `src/routes`.

## Database migrations

Apply the Supabase migrations in `supabase/migrations` before validating new control surfaces. Recent additions include the Monitoring Watchlist, Decision Log, workspace emergency-stop state and retirement of legacy prohibited X queue actions.

The new control tables are accessed through authenticated server functions. Direct anonymous/authenticated browser access is revoked in the migration.

## Environment and secrets

Keep credentials only in the deployment environment or approved secret store. Do not commit `.env` files, API keys, account cookies, service-role credentials, passwords or proxy credentials to Git.

Required environment-variable names are defined by the existing integrations. At minimum, deployments need the configured Supabase client/server variables and any already-connected provider credentials used by the enabled monitoring or AI features.

## Lovable sync

This project is connected to Lovable. Before publishing after a GitHub sync:

1. Pull/sync the intended GitHub branch into Lovable.
2. Apply pending Supabase migrations.
3. Allow TanStack Router to regenerate `src/routeTree.gen.ts` during build.
4. Run tests, production build, TypeScript and ESLint validation.
5. Verify `/overview`, `/mentions`, `/new`, `/campaign-manager`, `/campaign-proof`, `/reports`, `/preflight`, `/crisis`, `/brief`, `/watchlist`, `/decisions` and admin health surfaces.
6. Confirm environment secrets are configured in Lovable Cloud and are not stored in the repository.
